# Архитектура

## Ответственность модулей

| Модуль | Назначение |
|---|---|
| `cli.py`, `__main__.py` | Аргументы и завершение команды |
| `bootstrap.py` | Сборка зависимостей и владение ресурсами |
| `config.py` | Настройки и пути к данным |
| `polling.py` | Получение обновлений и обслуживание очереди |
| `conversation/routing.py` | Типизированное решение LLM, музыкальные параметры, строгая проверка JSON и повтор |
| `conversation/service.py` | Решение об ответе, интервалы, очередь, отправка |
| `conversation/context.py` | Построение контекста из сообщений |
| `conversation/ports.py` | Структурные контракты зависимостей |
| `generation/service.py` | Получение нот/аранжировки, валидация и повторы |
| `generation/prompts.py` | Типизированный каталог, загрузка и проверка шаблонов |
| `resources/prompts.toml` | Все инструкции модели, персонаж и проверочные запросы |
| `integrations/` | Telegram и OpenClaw |
| `storage/` | SQLite и сохранение интервалов |
| `audio/jobs.py` | Запуск и остановка аудиопроцесса |
| `audio/worker.py` | Проверка задания на границе процесса |
| `audio/pipeline.py` | Последовательность создания аудио |
| `audio/composers.py` | Стратегии: готовая партитура и NanoMaestro |
| Остальные `audio/` | Модели, валидация, озвучивание, речь, сведение, кодирование |

Объекты получают зависимости через конструкторы. Обработчик диалога не создаёт соединений и HTTP-клиентов. AsyncExitStack закрывает ресурсы при выходе и исключениях. SqliteConversationStore объединяет связанные SQL-операции над одной базой; сборка контекста вынесена из хранения.

Классы используются для компонентов с состоянием, ресурсами или отдельным жизненным циклом. Чистые преобразования остаются функциями. Задания и результаты описаны dataclass, музыкальные JSON-структуры — TypedDict. Protocol позволяет подменять зависимости без обязательного наследования.

## Паттерны и аудио

Adapter используется для интеграций, Strategy — для композиторов, Facade — для управления аудиозаданием. Стратегия выбирается небольшой функцией. Отдельной иерархии фабрик, глобального Singleton или контейнера зависимостей нет.

Основной бот не импортирует NumPy, ONNX Runtime, PyTorch и Piper при запуске. Worker загружает нужные библиотеки, выполняет одно задание и завершается до отправки аудио. Он запускается через `python -m semen_banan.audio.worker`; при отмене и таймауте останавливается дерево процессов. Кеш моделей ограничен процессом worker или ручного инструмента.

## Перенос и совместимость

Целевая версия — Python 3.13. Зависимости и настройки инструментов собраны в pyproject.toml; requirements-файлы оставлены как совместимые команды установки пакета.

База, интервалы, .env и модели остаются на прежних путях. Схема SQLite сохранена. Перед переносом сохранены текущие исходники, база через SQLite backup API и state.json в .runtime/backups/.

Старые корневые Python-модули заменены пакетами, тесты перенесены в tests/, установщик и сравнения — в tools/. Тестовый синтезатор render_wav, не использовавшийся рабочим аудиопутём, удалён; кодирование проверяется настоящим аудиопроцессом. Результаты старых экспериментов и неиспользуемый TimGM6mb убраны из рабочей структуры в локальную резервную копию. Основной банк GeneralUser GS и лицензии сохранены.

## Проверки и следующий этап

Проверки покрывают обработку сообщений, контекст, восстановление очереди, контракт Gateway, voice, изоляцию моделей и остановку процессов. Диагностические тесты проверяют создание музыки без Telegram и изменения рабочих данных. Реальный Gateway проверяется отдельными командами диагностики.

Следующий этап — логирование: единая конфигурация, время и контекст событий, уровни, ротация, диагностика worker и исключение секретов. На текущем этапе сохранено прежнее поведение журналов; логгеры получают имена модулей.

## Контракт маршрутизации

`OpenClawClient.classify()` передаёт сообщение, контекст и метаданные отдельной системной инструкции из раздела `[routing]` в `resources/prompts.toml`. `MessageRouter` проверяет результат и при необходимости один раз запрашивает исправление JSON. `ConversationService` применяет решение; `MusicGenerator` получает уже выбранные параметры через обязательный аргумент `options`, без анализа текста.

Пример ответа маршрутизатора:

```json
{
  "mode": "music",
  "trigger": "direct",
  "parameters": {"composer": "nanomaestro", "drums": true, "speech": false},
  "style_request": null
}
```

У `ignore` и `text` параметры равны null. Для `ignore` тип обращения — `none`; для ответов допустимы `direct`, `chain`, `request` и `banana`. Банановый режим допускает только текст и не меняет характер. `style_request` — отдельная инструкция до 500 символов либо null.

В очередь передаётся сообщение с внутренним полем `_routing`, содержащим проверенное решение. На повторе оно разбирается тем же валидатором. Старые задания без поля проходят классификацию, а UPSERT обновляет не только время, но также тип и JSON задания. Входящее сообщение сначала сохраняется для контекста; после определения обращения его признак цепочки может быть повышен, но не сброшен.

## Типы и оформление

`conversation/models.py` описывает контекст, личность бота, метаданные маршрутизации и строки истории. `audio/models.py` описывает ноты и аудиозадания. Тип стереосэмплов вынесен в `audio/types.py` и подключается через `TYPE_CHECKING`, чтобы аннотации не загружали NumPy в основной процесс. Тип PiperVoice также импортируется только для проверки типов.

`PromptCatalog` читает единый TOML-файл, проверяет обязательные строки и подстановки. Каталог можно передать клиенту OpenClaw через конструктор, а стандартный экземпляр кешируется. Рабочие данные и схема SQLite при этом не меняются. Правила оформления описаны в [code-style.md](code-style.md).

## Точные музыкальные параметры

`audio/customization.py` содержит разрешённые тембры General MIDI и AudioCustomization. Проверяются длительность 5–60 секунд, темп 60–180 BPM, от одного до четырёх уникальных инструментов и громкости 0–100%. В RouteDecision параметры объединяются с composer/drums/speech; старый трёхполевой формат по-прежнему принимается.

MusicGenerator передаёт параметры композитору, принудительно применяет выбранный темп к проверенной партитуре и рассчитывает длину аранжировки. AudioJobRunner сериализует AudioCustomization в задание; worker повторяет проверку и применяет тот же темп и длину аранжировки. Формат таблиц SQLite не меняется.

AudioPipeline разворачивает базовую фразу повторениями, озвучивает выбранные тембры и отдельно строит бас по аккордам. FluidSynth получает фактический номер программы. Для длинных записей граница нот расширена до 256 долей и 12 000 событий нот.

Сведение ограничивает или дополняет дорожки до точного числа сэмплов, применяет отдельные уровни и короткое финальное затухание. При пользовательском балансе автоматическая итоговая нормализация отключается, иначе она отменяла бы изменение громкости единственного инструмента. Общий уровень применяется при кодировании. Без новых параметров используется прежний путь сведения.

Параметры хранятся в сериализованном решении очереди; повтор и перезапуск не запускают новую классификацию. История записи содержит фактическую длину, темп, инструменты и уровни, чтобы модель могла понимать последующие уточнения.


Настройки речи представлены `VoiceSettings` и `VoiceEffect`: проверяются при разборе маршрута и задания рабочего процесса. `AudioCustomization.voice_settings` переносит их через очередь. Silero синтезирует речь в 48 кГц с автоматическими ударениями. Piper остаётся доступен для прежнего голоса. Затем `apply_voice_effects` локально меняет высоту с компенсацией темпа и подмешивает один эффект средствами FFmpeg. Кеш синтеза учитывает текст и все параметры голоса. Доступны фиксированные имена голосов Silero и Denis; имена моделей и фильтры от LLM не исполняются. Старые задания с явно сохранённым denis сохраняют этот голос. Скорость Silero меняется через atempo с сохранением высоты.

Оба варианта сведения используют одну `speech_ducking_envelope`: плавная зависимость от энергии речи, максимальное ослабление инструментов 20%, барабанов 10%. Речь нормализуется до RMS 0.13 перед пользовательской громкостью.


## Изображения

`images/models.py` содержит строгие `ImageOptions` и `ImageReply`. `ReplyMode.IMAGE` и `RouteDecision.image` добавляют параметры в существующий JSON очереди без изменения схемы SQLite. `ConversationService` использует `OpenClawImageGenerator` и `TelegramClient.send_photo`; текстовый Gateway остаётся без вызовов инструментов.

`integrations/openclaw_images.py` вызывает штатную команду OpenClaw отдельным процессом. Передаётся фиксированный набор аргументов; описания не исполняются в оболочке. В Windows с WSL используется явно настроенный дистрибутив, временный результат создаётся в `/tmp` и читается через `\\wsl.localhost\<дистрибутив>\tmp`, внешний `timeout` ограничивает жизнь Linux-команды. Общий `processes.stop_worker` завершает дочерние процессы при отмене или таймауте. Для WSL внешний таймер также ограничивает процесс внутри дистрибутива после отключения Windows-клиента.

PNG/JPEG/WebP проверяются Pillow, нормализуются и атомарно сохраняются как JPEG. Имя кеша — SHA-256 идентификатора сообщения, параметров и модели. Поэтому повтор отправки не вызывает новую генерацию. Удаляются только фото с именами кеша старше семи суток. `ImageGenerationError` даёт видимый текстовый ответ; временная ошибка отправки Telegram использует обычную очередь. Успешный ответ сохраняется как описание изображения в истории. Редактирование входных изображений и одновременная генерация песни с обложкой не входят в текущий режим.


## Постоянный контекст группы

`group.py` загружает неизменяемый `GroupCatalog` с участниками из внешнего `group.toml`. Файлы фотографий задаются относительно `assets/participants`, выход из этого каталога запрещён. `GroupCatalog.context()` возвращает только текстовые сведения и номера фотографий. `GroupCatalog.photos()` отдельно читает и подготавливает все фото после положительного решения модели. В текущем варианте допускается до пяти участников, что соответствует лимиту входных образцов выбранного генератора.

`RouteDecision.load_participant_photos` — новое необязательное поле с безопасным значением по умолчанию `false`. Оно хранится в JSON очереди без миграции SQLite. Сервис переносит флаг в `ContextMessage` для последующих запросов LLM и в параметр генератора картинок. Первичная классификация фотографий не получает.

`OpenClawClient.user_content()` добавляет справочник во все запросы, а при флаге — пять пар «подпись — image_url». Инструкции работы со справочником и шаблон описания картинки находятся в `[group]` общего `prompts.toml`. В генераторе флаг переключает `generate` на `edit` и добавляет пять файлов. Подготовленные образцы временно размещаются в среде OpenClaw и удаляются после запроса; в Windows используется доступ к файлам WSL. Ключ кеша картинки включает справочник и хеши переданных фото. Поэтому изменение фото не подменяется старым кешем, а обычный повтор отправки не запускает новую генерацию.


## Случайные реплики

`ConversationService` применяет две независимые вероятности после классификации `ignore` или `banana`. Внутренний `ReplyTrigger.SPONTANEOUS` сохраняет смысл выбранного события, `ReplyMode.VOICE` означает озвучивание обычного ответа. Эти значения допустимы в сохранённом решении, но `MessageRouter` отклоняет их, если их вернула LLM: решение о случайном ответе принадлежит приложению. Параметры фотографий, музыкальные задания и изменения характера для такого решения не включаются. В запрос генерации реплики передаётся `spontaneous_reply=true`.

`AudioJobRunner.speak()` и `render()` используют общий `_run_request()` и прежнюю изоляцию процесса. `audio.worker` распознаёт речевое задание по `kind=speech`, создаёт последовательность фраз и кодирует OGG/Opus без музыкального пайплайна. `conversation/style.normalize_reply_style()` обеспечивает обязательное оформление в дополнение к инструкции модели.


## Смысловые реакции

`ReactionService` вызывается отдельно перед обычной обработкой и имеет собственную проверку допустимости: разрешённая группа, свежее сообщение другого автора, наличие текста или медиа. В отличие от обычных ответов, допускаются другие боты и медиа без подписи. Обновления реакций не запрашиваются, поэтому циклов на чужие реакции нет.

Модель возвращает признак явной просьбы, признак обращения и подходящий эмодзи. Явная просьба обходит вероятность. Для самостоятельной реакции используется одно равномерное случайное число, которое сравнивается с вероятностью соответствующей категории; повторного розыгрыша нет. Это сохраняет 0.1 и 1/3, не перемножая их. Модель выбирает смысл реакции, приложение — факт её отправки.

`OpenClawClient.select_reaction()` получает контекст, сведения о группе, признаки обращения, тип сообщения и разрешённые эмодзи. Фото участников не загружаются. `ReactionSelection` проверяет JSON и эмодзи; `ReactionService` отправляет результат через существующий `Telegram.call`. Выбор ограничен 15 секундами или меньшим общим таймаутом Gateway. Ошибки логируются и не влияют на обычные ответы. Схема очереди и JSON основной маршрутизации не изменяются.

Явная просьба Семёну поставить реакцию на текущее сообщение выполняется без розыгрыша, даже при нулевых вероятностях самостоятельных реакций. LLM определяет `explicit_request` и запрошенный эмодзи. Для этого смысловой анализ выполняется для каждого допустимого сообщения с доступными реакциями; предварительный случайный пропуск не используется. Ограничения Telegram и проверка эмодзи сохраняются.
